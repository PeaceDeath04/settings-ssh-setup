## 1. КРИТИЧНО — скрипт вообще не запускается

**Строки 1683–1685: незакрытая кавычка.**

```bash
FINAL_USER="$(
    awk '$1=="allowusers"{print $2; exit}' <<< "$FINAL_CONFIG"
)          # <-- здесь не хватает закрывающей  "
```

Проверка:

```
$ bash -n setup-ssh-settings.sh
setup-ssh-settings.sh: line 1757: unexpected EOF while looking for matching `"'   (exit 2)

$ shellcheck setup-ssh-settings.sh
SC1078: Did you forget to close this double quoted string?
SC1072: Expected end of double quoted string.
```

bash разбирает файл целиком до выполнения, поэтому **текущая версия из репозитория
не может выполниться ни разу** — ни установка, ни `--rollback`. Всё, что написано
после строки 1685 (финальные проверки, итоговый вывод, предупреждение «не закрывайте
сессию»), проваливается в незакрытую строку.

Исправление — добавить `"` после `)` на строке 1685. После этого `bash -n` проходит,
и shellcheck остаётся чистым (единственное замечание — ожидаемый SC1091 на
`source metadata`).

## 2. ВЫСОКИЙ приоритет

### 2.1. `ufw delete` без `--force` — интерактивный запрос и зависание rollback

Строки 305, 483, 1290:

```bash
sudo ufw delete allow 22/tcp            # основной сценарий (строка 1290)
sudo ufw delete allow "$SSH_PORT/tcp" >/dev/null 2>&1 || true   # rollback (305, 483)
```

`ufw delete` **всегда** спрашивает `Deleting: allow 22/tcp — Proceed with
operation (y|n)?`, если не передан `--force`.

Последствия:
- в основном сценарии скрипт «зависает» на скрытом от логики промпте — пользователь
  не ожидает вопроса посреди автоматического шага; ввод `n` → ненулевой код →
  `set -e` → rollback;
- в `rollback()` и `manual_rollback()` stdout/stderr перенаправлены в `/dev/null`,
  но **stdin остаётся терминалом**: ufw молча ждёт ввод → **rollback зависает
  навсегда без какого-либо вывода**. Если stdin закрыт — ufw получает EOF, операция
  отменяется, правило не удаляется, а `|| true` это скрывает.

Исправление: везде `sudo ufw --force delete ...`.

### 2.2. Ручной rollback не удаляет правило нового порта (пустой `$SSH_PORT`)

Строки 481–486 (`manual_rollback`):

```bash
sudo ufw delete allow "$SSH_PORT/tcp" >/dev/null 2>&1 || true
ok "Правило $SSH_PORT/tcp удалено."
```

В `--rollback`-режиме `SSH_PORT` нигде не устанавливается (в `metadata` он не
сохраняется, повторного ввода нет) → команда превращается в
`ufw delete allow /tcp` → ошибка → проглатывается `|| true` → **дыра в firewall
остаётся**, а скрипт рапортует «Правило /tcp удалено».

Исправление: сохранять `BACKUP_SSH_PORT='$SSH_PORT'` в `metadata` при создании
backup и использовать его в `manual_rollback`.

### 2.3. Проверка правил UFW игнорирует источник (source)

Строки 1248, 1268, 1305, 1321 и аналоги:

```bash
grep -qE "^${SSH_PORT}/tcp[[:space:]]+ALLOW"
```

Эмпирически проверено: правило `33333/tcp ALLOW 10.0.0.5` (разрешено только одному
адресу) удовлетворяет паттерну. Сценарий локаута:

1. на сервере уже есть `ALLOW` для случайно выбранного порта, но с ограничением по IP;
2. скрипт считает «порт уже разрешён» и **не добавляет** общее правило;
3. sshd переезжает на этот порт, а UFW пускает только 10.0.0.5 → доступ теряют все.

Обратный случай: если правило для 22 source-specific
(`22/tcp ALLOW 1.2.3.4`), то `ufw delete allow 22/tcp` завершится ошибкой
«Could not delete non-existent rule» → `set -e` → откат.

Исправление: парсить вывод `ufw status` с учётом колонки From (требовать `Anywhere`),
или удалять/добавлять правила по номерам через `ufw status numbered`.

### 2.4. Случайный порт попадает в диапазон эфемерных портов

Строка 676: `shuf -i 20000-60000 -n 1`.

Дефолтный `net.ipv4.ip_local_port_range` в Linux — **32768–60999** (подтверждено:
`cat /proc/sys/net/ipv4/ip_local_port_range` → `32768 60999`). То есть ~2/3
диапазона скрипта пересекается с эфемерными портами: любое исходящее соединение
сервера может временно занять выбранный порт, и после следующего рестарта/перезагрузки
sshd не сможет его занять («Address already in use»), а ssh.socket уйдёт в failed.

Исправление: генерировать порт в 20000–32767 либо резервировать выбранный порт:
`sysctl -w net.ipv4.ip_local_reserved_ports=PORT` (+ запись в `/etc/sysctl.d/`).

## 3. СРЕДНИЙ приоритет

### 3.1. `trap rollback EXIT` срабатывает ещё до внесения изменений

`trap rollback EXIT` ставится на строке 579 — **до** интерактивных вопросов
(строки 620+). Отмена на первом же промпте («Отменено») или fehlende команда
запускает rollback, который в конце безусловно делает (строки 366–378):

```bash
sudo systemctl daemon-reload || true
sudo systemctl restart ssh.socket || true
sudo systemctl restart "$SSH_SERVICE" || true
```

На дефолтной 24.04 (socket-активация, `ssh.service` не активен) `restart ssh.service`
**запускает** sshd -D на порту 22 → конфликт с `ssh.socket` → failed-unit.
То есть даже простой отказ от установки оставляет систему в странно-грязном
состоянии и печатает «Попытка откатить изменения... Backup: ...», которого нет.

Исправление: в начале `rollback()` — early return, если ни один флаг изменений
не поднят (`BACKUP_CREATED`, `USER_CREATED`, `KEY_ADDED`, socket-изменения).

### 3.2. Конец rollback всегда рестартует и socket, и service

Строки 369–378 и 540–549. Как в 3.1: одновременный запуск `ssh.socket` и
`ssh.service` на одном порту даёт failed-unit (скрыт `|| true`). Рестартовать нужно
только тот механизм, который реально использовался до/после изменений
(`systemctl is-active ssh.socket`).

### 3.3. `install -g "$SSH_USER"` для существующего пользователя

Строки 921–927:

```bash
sudo install -d -m 700 -o "$SSH_USER" -g "$SSH_USER" "$USER_HOME/.ssh"
```

Если пользователь уже существовал и его основная группа **не** совпадает с именем
(обычное дело), `install` завершится ошибкой → die → rollback. Надёжнее:
`-g "$(id -gn "$SSH_USER")"`.

### 3.4. `CURRENT_USER="$(id -un)"` под sudo возвращает `root`

Строка 612. Скрипт по инструкции запускается как `sudo ./setup-ssh-settings.sh`,
поэтому `id -un` = `root`, и предупреждение «Пользователь root больше не сможет
входить» относится не к тому, кто реально потеряет доступ (например, `ubuntu` из
cloud-образа). Нужно `CURRENT_USER="${SUDO_USER:-$(id -un)}"`.

### 3.5. Проверка AllowUsers смотрит только первого пользователя

Строки 1074–1082, 1108, 1683. `sshd -T` выводит все разрешённые имена одной строкой
(`allowusers user1 user2`), а `awk '{print $2}'` берёт только первое слово.
Директивы AllowUsers из разных файлов **суммируются**; если в основном конфиге уже
был `AllowUsers someone`, а Include стоит вверху (как в Ubuntu), эффективная строка —
`allowusers <наш> someone`, проверка `$2 == SSH_USER` **пройдёт**, но `someone`
сохранит доступ. Сравнивать нужно всю строку после первого поля.

### 3.6. Асимметрия: ручной rollback не удаляет созданного пользователя

Автоматический rollback удаляет созданного скриптом пользователя (`userdel -r`),
а `manual_rollback` — нет, и созданный `authorized_keys` (когда файла раньше не было)
тоже остаётся. После `--rollback` в системе остаётся sudo-пользователь с ключом.
Если это осознанное решение — стоит задокументировать; иначе — повторить логику
автоматического отката (флаг `USER_CREATED` нужно сохранять в metadata).

### 3.7. `ssh-keygen -lf -` принимает и приватные ключи

Строки 714–721. Если по ошибке вставить **приватный** ключ, `ssh-keygen -lf`
успешно отработает, и приватный ключ окажется в `authorized_keys` и в backup.
Дополнить проверку: ключ должен начинаться с `ssh-rsa|ssh-ed25519|ecdsa-sha2-*|sk-*`.

### 3.8. `source "$CURRENT_BACKUP/metadata"`

Строка 423. Файл root-owned, но `source` исполняет произвольный код; путь
`BACKUP_AUTHORIZED_KEYS_PATH='...'` ломается, если в пути встретится `'`.
Безопаснее читать значения через `grep/cut` без исполнения.

## 5. Что сделано хорошо

- `set -euo pipefail`, аккуратное цитирование, `PATH`-hardening в начале;
- валидация всех входных данных: regex на имя пользователя, диапазон порта,
  проверка ключа через `ssh-keygen`;
- правильная работа с socket-активацией 24.04: drop-in `ListenStream=` (сброс)
  + новое значение; (в 24.04 есть ещё `sshd-socket-generator`, автоматически
  синхронизирующий ListenStream из конфига sshd — ручной drop-in ему не мешает,
  значения совпадают, но фактически дублирует его работу);
- многоуровневая верификация: `sshd -t`, `sshd -T`, реальный listening-порт через
  `ss`, баннер через `/dev/tcp`, права файлов — сильная защита от «настроил и
  потерял доступ»;
- корректный порядок UFW-операций в основном сценарии: сначала разрешить новый
  порт, потом удалить 22;
- awk-разбор `ss` корректно обрабатывает IPv4/IPv6/wildcard и не даёт ложных
  срабатываний (`:2222` не матчится на порт 22) — проверено тестом;
- backup + два механизма отката; понятные предупреждения не закрывать сессию.
