# SSH Hardening Setup

Bash-скрипт для базового усиления безопасности SSH на Ubuntu Server/VPS.

Скрипт создаёт или настраивает отдельного SSH-пользователя, устанавливает публичный SSH-ключ, отключает вход `root` и парольную авторизацию, меняет SSH-порт, настраивает `systemd ssh.socket` при необходимости и обновляет правила UFW.

Дополнительно скрипт создаёт backup перед изменениями и поддерживает автоматический rollback при ошибке.

> ⚠️ **Важно:** не закрывайте текущую SSH-сессию, пока не проверите новое подключение к серверу через новый порт и нового пользователя.

---

## Возможности

Скрипт выполняет следующие действия:

* создаёт SSH-пользователя или использует существующего;
* добавляет пользователя в группу `sudo`;
* проверяет указанный публичный SSH-ключ через `ssh-keygen`;
* устанавливает SSH-ключ в `authorized_keys`;
* не перезаписывает существующий `authorized_keys`;
* отключает вход `root` через SSH;
* отключает авторизацию по паролю;
* отключает `keyboard-interactive` авторизацию;
* разрешает авторизацию по публичному ключу;
* ограничивает SSH-доступ через `AllowUsers`;
* позволяет выбрать SSH-порт или автоматически генерирует случайный порт;
* поддерживает диапазон портов `20000–60000`;
* проверяет, свободен ли выбранный порт;
* проверяет итоговую конфигурацию через `sshd -t` и `sshd -T`;
* настраивает `systemd ssh.socket`, если он используется;
* добавляет новый SSH-порт в UFW;
* удаляет разрешение `22/tcp` из UFW;
* не считает порт разрешённым, если правило UFW ограничено по источнику (source-specific);
* резервирует SSH-порт в `net.ipv4.ip_local_reserved_ports`, если он попадает в диапазон эфемерных портов;
* проверяет, что новый SSH-порт действительно слушается;
* проверяет, что порт `22` больше не слушается;
* проверяет локальный SSH banner;
* проверяет права на `.ssh` и `authorized_keys`;
* создаёт backup изменяемых конфигурационных файлов и хранит 10 последних backup;
* автоматически выполняет rollback при ошибке;
* поддерживает ручной rollback через `--rollback`.

## Требования

Скрипт рассчитан прежде всего на Ubuntu Server.

Необходимы:

* `bash`;
* `sudo`;
* `openssh-server`;
* `openssh-client` / `ssh-keygen`;
* `systemd`;
* `iproute2` / `ss`;
* `ufw` — опционально.

Запускать скрипт необходимо от пользователя, имеющего права `sudo`.

## Установка

Скачать репозиторий:

```bash
git clone https://github.com/PeaceDeath04/settings-ssh-setup.git
cd settings-ssh-setup
```

Сделать скрипт исполняемым:

```bash
chmod +x setup-ssh-settings.sh
```

Запустить:

```bash
sudo ./setup-ssh-settings.sh
```

## Что потребуется ввести

При обычном запуске скрипт запросит три параметра.

### SSH-пользователь

```text
Имя главного SSH-пользователя:
```

Например:

```text
admin
```

Пользователь получит права `sudo`.

`root` использовать в качестве нового SSH-пользователя нельзя: скрипт отключает SSH-вход для `root`.

### SSH-порт

```text
SSH-порт [Enter = случайный 20000-32767]:
```

Можно указать собственный порт:

```text
49268
```

или просто нажать `Enter`.

В таком случае скрипт случайным образом выберет порт из диапазона:

```text
20000–32767
```

Диапазон намеренно заканчивается на `32767`: стандартный диапазон эфемерных портов Linux (`net.ipv4.ip_local_port_range`) начинается с `32768`. Случайный порт из эфемерного диапазона может быть временно занят исходящим соединением, и sshd не сможет запуститься после рестарта.

Если вы вручную указываете порт, попадающий в эфемерный диапазон (`32768–60999` по умолчанию), скрипт дополнительно резервирует его через `net.ipv4.ip_local_reserved_ports` (файл `/etc/sysctl.d/99-ssh-setup-reserved-port.conf`).

Перед настройкой скрипт проверяет, что выбранный порт не занят другим локальным сервисом.

### Публичный SSH-ключ

```text
Ваш публичный SSH-ключ:
```

Например:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... user@computer
```

Использовать необходимо именно **публичный** ключ.

Приватный ключ (`.ppk`, `id_ed25519`, `id_rsa` и т. п.) вводить в скрипт **нельзя**.

Перед изменением системы ключ проверяется через `ssh-keygen`.

## Что происходит с SSH

Скрипт создаёт конфигурацию:

```text
/etc/ssh/sshd_config.d/01-my-settings-ssh.conf
```

Основные параметры:

```text
Port <выбранный порт>

PermitRootLogin no

PasswordAuthentication no

KbdInteractiveAuthentication no

PubkeyAuthentication yes

AllowUsers <выбранный пользователь>
```

Также устанавливаются базовые дополнительные ограничения:

```text
MaxAuthTries 4
LoginGraceTime 30
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no
```

Таким образом:

* `root` больше не может войти через SSH;
* парольная авторизация отключена;
* `keyboard-interactive` отключён;
* разрешён вход по SSH-ключу;
* подключаться через SSH может только указанный пользователь;
* SSH работает через выбранный порт;
* X11 forwarding и SSH forwarding отключены.

> Если вам необходим `AllowTcpForwarding` или другой механизм SSH forwarding, проверьте совместимость этой настройки со своим сценарием использования перед запуском.

---

## `sshd_config.d` и порядок конфигурации

Скрипт использует отдельный файл:

```text
/etc/ssh/sshd_config.d/01-my-settings-ssh.conf
```

В стандартной конфигурации Ubuntu дополнительные файлы подключаются через:

```text
Include /etc/ssh/sshd_config.d/*.conf
```

Файлы из каталога обрабатываются в лексикографическом порядке.

Имя `01-my-settings-ssh.conf` позволяет загрузить настройки раньше файлов с именами вроде:

```text
50-cloud-init.conf
```

Однако итоговая конфигурация зависит от всей конфигурации SSH. Поэтому скрипт дополнительно проверяет **эффективные параметры** через:

```bash
sshd -T
```

Если итоговая конфигурация не соответствует требуемым параметрам, скрипт завершает работу с ошибкой и запускает rollback.

## systemd `ssh.socket`

На некоторых системах SSH использует systemd socket activation.

В таком случае одного изменения `sshd_config` недостаточно: `ssh.socket` также может определять порт, на котором принимаются новые подключения.

Если `ssh.socket` обнаружен, скрипт создаёт:

```text
/etc/systemd/system/ssh.socket.d/override.conf
```

с настройкой выбранного SSH-порта.

После изменения выполняется:

```bash
systemctl daemon-reload
systemctl restart ssh.socket
```

Если `ssh.socket` не используется, скрипт перезапускает обычный SSH service.

## UFW

Если UFW активен, скрипт:

1. проверяет состояние firewall;
2. проверяет, было ли разрешено `22/tcp` до запуска;
3. разрешает новый SSH-порт;
4. удаляет разрешение `22/tcp`;
5. проверяет, что новый порт разрешён;
6. проверяет, что `22/tcp` больше не разрешён.

Например, после настройки:

```text
49268/tcp ALLOW
```

вместо:

```text
22/tcp ALLOW
```

Если UFW не установлен или не активен, правила UFW не изменяются.

> ⚠️ Если у VPS есть отдельный firewall/security group у хостинг-провайдера, новый SSH-порт необходимо разрешить и там. Скрипт изменяет только локальный UFW.

## Backup

Перед изменением конфигурации создаётся отдельный backup в:

```text
/root/ssh-hardening-backups/
```

Текущий backup доступен через:

```text
/root/ssh-hardening-backups/current
```

Хранится 10 последних backup, более старые удаляются автоматически (ротация).

В backup сохраняются изменяемые конфигурационные файлы, в частности:

```text
sshd_config
socket-override
authorized_keys
metadata
```

Это позволяет восстановить состояние SSH после неудачной настройки.

## Автоматический rollback

Скрипт использует автоматический rollback.

Если во время выполнения происходит ошибка после создания backup, скрипт пытается восстановить:

* предыдущий SSH-конфиг;
* предыдущий `ssh.socket` override;
* предыдущий `authorized_keys`;
* состояние правила `22/tcp` в UFW;
* правило нового SSH-порта, если оно было добавлено самим скриптом.

Если пользователь был **создан самим скриптом во время неудачного запуска**, автоматический rollback также пытается удалить этого пользователя.

Существующий пользователь автоматически не удаляется.

---

## Ручной rollback

Последний созданный backup можно восстановить вручную:

```bash
sudo ./setup-ssh-settings.sh --rollback
```

Запускать rollback необходимо именно через `sudo` (backup лежит в `/root`, права `700`).

Скрипт попросит подтвердить операцию.

Ручной rollback восстанавливает конфигурационные файлы, UFW и `authorized_keys`.

Если пользователь был **создан самим скриптом**, rollback дополнительно предложит удалить его (вместе с домашним каталогом) — это действие выполняется только после отдельного подтверждения.

Существующие пользователи не удаляются никогда: удаление пользовательского аккаунта автоматически может привести к потере доступа или удалению нужных данных.

## Проверки

Перед завершением скрипт выполняет несколько уровней проверки.

### Проверка синтаксиса

```bash
sshd -t
```

Проверяет, что SSH-конфигурация синтаксически корректна.

### Проверка эффективной конфигурации

```bash
sshd -T
```

Проверяются:

* SSH-порт;
* `PermitRootLogin`;
* `PasswordAuthentication`;
* `KbdInteractiveAuthentication`;
* `PubkeyAuthentication`;
* `AllowUsers`.

### Проверка реального listening port

Проверяется через:

```bash
ss -lntp
```

Это важно: наличие `Port` в конфигурации ещё не гарантирует, что именно этот порт реально слушается системой.

Скрипт проверяет:

* что новый SSH-порт слушается;
* что `22` больше не слушается.

### Локальная проверка SSH banner

Дополнительно выполняется локальное подключение к выбранному TCP-порту и проверяется наличие SSH banner.

Например:

```text
SSH-2.0-OpenSSH_...
```

### Проверка пользователя

Проверяется:

* существование пользователя;
* наличие пользователя в группе `sudo`;
* наличие домашнего каталога.

### Проверка SSH-ключа

Проверяются:

```text
~/.ssh
```

с правами:

```text
700
```

и:

```text
authorized_keys
```

с правами:

```text
600
```

## После установки

После успешного завершения скрипт покажет команду для нового подключения:

```bash
ssh -p <SSH_PORT> <SSH_USER>@IP_СЕРВЕРА
```

Например:

```bash
ssh -p 49268 admin@203.0.113.10
```

**Не закрывайте текущую SSH-сессию.**

Сначала откройте новое подключение в отдельном окне терминала и убедитесь, что оно работает.

Только после успешной проверки можно закрывать старую SSH-сессию.

## Безопасность

Скрипт не содержит:

* приватных SSH-ключей;
* паролей;
* API-токенов;
* Cloudflare API keys;
* credentials VPS.

Публичный SSH-ключ не является секретом и может использоваться в `authorized_keys`.

Не добавляйте в репозиторий:

```text
*.ppk
*.pem
id_rsa
id_ed25519
.env
.env.*
credentials.*
secrets.*
```

Рекомендуется использовать `.gitignore`.

---

## Важные предупреждения

Этот скрипт изменяет критические параметры SSH.

Ошибка в SSH-конфигурации или потеря приватного ключа может привести к потере доступа к серверу.

Перед запуском убедитесь, что:

* у вас есть рабочий приватный SSH-ключ;
* публичный ключ соответствует приватному;
* текущая SSH-сессия остаётся открытой;
* у вас есть доступ к консоли VPS или другому аварийному доступу;
* новый SSH-порт разрешён в firewall/security group провайдера, если такой firewall используется.

**Никогда не закрывайте единственную рабочую SSH-сессию сразу после запуска.**

---

## Ограничения

Скрипт предназначен для базового SSH hardening и не является полноценным security-аудитом сервера.

Он не настраивает:

* fail2ban;
* VPN;
* firewall policy для приложений;
* автоматические обновления;
* аудит системы;
* SELinux/AppArmor;
* мониторинг;
* резервное копирование VPS;
* cloud firewall/security groups провайдера.

Конкретная конфигурация VPS, Docker, cloud-init, systemd и OpenSSH может отличаться, поэтому после выполнения скрипта необходимо проверить подключение вручную.
